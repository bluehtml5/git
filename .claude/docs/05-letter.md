# 給未來 session 的信

> 寫於 2026-07-03，Fable 5。這封信講三件使用者沒問、但對這個環境最重要的事，以及這套制度最可能怎麼壞掉。你（讀信的模型）不需要照單全收，但推翻任何一條之前，請先確認你有比我當時更多的證據。

## 第一件事：這個 repo 目前是空殼，制度才是本體

我建制度時，repo 裡只有一個測試用 readme（內容是 `//測試`）。也就是說：**這套制度還沒有跟任何真實專案磨合過**，選型表、模板、判準都是針對「這個 harness 的通病」設計的，不是針對使用者的實際工作。當真正的專案進來（不管是塞進這個 repo 還是用 `add_repo` 接別的 repo），第一個 session 該做的事：
1. 把 `CLAUDE.md` ＋ `.claude/` 整套複製到真專案（或在真專案的 CLAUDE.md 裡指回這裡）。
2. 用一兩個真實任務跑一遍模板，把不合身的地方按 `04-maintenance.md` 的權限分級修掉，並記進 `lessons.md`。
3. 問使用者他實際的工作型態（寫什麼語言、產出給誰看、什麼算高風險），把 `02-judgment.md` 的「高風險」定義具體化——現在那條是通用寫法，磨合後應該變成他的專屬清單。

## 第二件事：hook 比規則可靠，能機械執法的就不要靠自覺

你是模型，你會忘規則——尤其 context 被壓縮之後。這個環境的 `~/.claude/` 裡已經有平台裝的 hooks（session 啟動時設 git identity、停止時檢查 git 狀態），證明這條路是通的。制度檔裡「隨做隨 push」「commit 前跑測試」這類規則，本質上都能做成 `settings.json` hook 讓 harness 強制執行，模型忘了也擋得住。**建議主動向使用者提一次**：用 `update-config` skill 把最常違反的規則 hook 化（他答應才做，hook 屬於 `04-maintenance.md` 裡「要先問」的等級）。提的時候講清楚 trade-off：hook 是硬的，擋住的時候不分青紅皂白。

## 第三件事：這個環境的 token 經濟有幾個暗坑

- **Prompt cache TTL 是 5 分鐘**。等外部事件時 sleep 或空轉超過 5 分鐘，下一輪整個 context 重讀，又慢又貴。等待一律用 `send_later` / `subscribe_pr_activity`（事件會推回 session），這不只是省錢，是這個環境的正確等待方式。
- **MCP 工具面很大**（GitHub 約百個工具，另有 Canva、Google Drive、Notion——Notion 未授權，用不了就直說，別重試）。ToolSearch 用 `select:工具名` 精準載入，不要用寬鬆關鍵字一次載一堆 schema 進 context。
- **scratchpad 和 `~/` 都會蒸發**。任何值得留的東西只有兩個去處：repo（commit+push）或使用者手上（SendUserFile／總結訊息）。

## 這套制度最可能的退化方式，與預防

1. **膨脹成沒人讀的長文**：每個 session 加一點「以防萬一」的規則，兩個月後 CLAUDE.md 五百行，弱模型只讀前 50 行。→ 預防已內建：CLAUDE.md 只准放路由和三條硬規則；`04-maintenance.md` 有行數觸發的精簡協議。請執行它，而不是繞過它。
2. **規則因為「當下很煩」被放寬**：重試上限、驗證不自驗，都是專門設計來對抗模型自然傾向的，也因此天天都會「很煩」。哪天有模型覺得「這次情況特殊可以跳過驗證」——那正是規則要擋的時刻。→ 放寬必須過使用者，`04-maintenance.md` 已寫死。
3. **驗證退化成橡皮圖章**：verifier 收到的驗收條件愈來愈空泛（「檢查品質 OK」），它就只能回 PASS。驗證的品質上限 = 驗收條件的具體度。→ 派工前自問：這條驗收條件 haiku 能機械判定嗎？不能就重寫。
4. **環境事實悄悄過時**：模型枚舉、工具名、MCP 面板都會變。制度檔講錯一個工具名，弱模型可能卡死或亂編替代品。→ `04-maintenance.md` 的健康檢查；發現事實錯誤屬於「可自修」等級，修就是了，附證據。

## 最後一句

這套制度的成敗不在規則多精妙，而在「照做的成本是否低於即興發揮」。所以維護方向永遠是：更短、更具體、更可機械檢查。做不到具體的，誠實標註「這是品味題」然後升級或問人——這就是我能留給你的全部判斷力了。
