# 快速診斷：這個 harness 最容易漏 token、失焦、出錯的三件事

> 寫於 2026-07-03，由 Fable 5 session 實測本環境後寫成。後面所有制度檔（01～05）都是針對這三個問題設計的。
> 本環境 = Claude Code on the web（遠端暫時性 container）＋ GitHub repo `bluehtml5/git` 作為唯一持久層。

## 第 1 名：主對話自己下場做探索，context 被原始資料塞爆

**症狀**：主模型直接用 Read 讀整個檔案、Grep 吐幾十筆結果、WebFetch 抓整頁——這些原始資料全部留在主對話 context 裡，之後再也用不到，卻一路佔著空間。context 滿了會被壓縮（compaction），壓縮最先犧牲的就是開頭的規則與使用者原始需求 → 模型「失憶」、開始重複做過的事或違反已講好的規則。

**實測證據**：本 session 一次 WebFetch 就回傳 73KB（被 harness 轉存成檔案）。GitHub MCP 的 `search_*`/`list_*` 不加參數時一次可吐數十筆完整 JSON。

**具體修法**（詳細規則在 `01-delegation.md`）：
1. **兩次原則**：主對話最多做兩次「定向」查找（明確知道檔名或關鍵字）。要掃 repo、要看多個檔案、要查網頁 → 一律派 subagent（`Explore` 或 `general-purpose`），只讓結論和 `檔案:行號` 回到主對話。
2. **大回傳先落檔再抽取**：工具回傳被存成檔案時（persisted-output），用 Grep 抽你要的那幾行，不要 Read 整檔。
3. **MCP 工具強制參數**：GitHub MCP 一律 `perPage: 5-10`、能用 `minimal_output: true` 就用。

## 第 2 名：進度不落地——container 會被回收，沒 push 的等於沒做

**症狀**：這個環境是暫時性的：session 閒置或結束後 container 整個消失，`~/`、scratchpad、未 commit 的工作樹全部蒸發。弱模型常見的錯誤是「全部做完再一次 commit」，中途斷線就整批歸零。

**具體修法**：
1. **每完成一個邏輯單位就 `git add` + `commit` + `push -u origin <指定分支>`**。「邏輯單位」= 一個能獨立描述的改動（一個檔案的完整初版、一個修好的 bug、一份寫完的文件）。判準：如果現在斷線，這個 commit 單獨存在是否仍有意義？是 → 該 push 了。
2. push 失敗只在網路錯誤時重試（2s/4s/8s/16s 最多 4 次），其他錯誤（權限、分支保護）停下來報告，不要硬試。
3. 長回合任務開始前，先確認自己在指定分支上（`git branch --show-current`）。

## 第 3 名：重試迴圈與空等——同一招連打三次、用 sleep 輪詢外部事件

**症狀**：弱模型遇到失敗傾向「再試一次一模一樣的」，或改一個無關緊要的細節再試，燒掉大量 token 卻不前進。另一種是等 CI、等外部狀態時用 `sleep` 輪詢，每輪都是一次完整推理成本。

**具體修法**：
1. **重試上限硬規則**：同一做法失敗 2 次 = 這條路關閉。第 3 次行動必須是以下之一：(a) 換一個本質不同的做法、(b) 升級模型重派（帶完整失敗軌跡，見 `01-delegation.md` 升降級路徑）、(c) 停下來把卡點報告給使用者。「本質不同」的判準：如果新嘗試失敗的理由會和上次一樣，就不算換路。
2. **禁止 sleep 輪詢**：等 PR 事件用 `subscribe_pr_activity`；等時間到用 `send_later`（claude-code-remote MCP）。這些會把事件推回 session，不用燒 token 空等。
3. **錯誤要先讀完再動手**：修錯前把錯誤訊息完整貼進自己的推理（不是掃一眼），確認修的是訊息裡指的那個問題，不是模式匹配到的「常見問題」。

## 誠實條款：這份診斷補不了的事

上面三條靠制度（拆解、派工、驗證、重試上限）就能補。但有一類問題制度補不了：**模糊需求與品味判斷**（命名好不好、架構取捨、文案語氣、使用者其實要什麼）。弱模型在這類問題上不是「執行差」而是「判斷差」，checklist 只能降低災難率，不能產生好品味。遇到時的正確動作寫在 `02-judgment.md` 的「品味題處理」一節：升級模型、多答案評審選優、或直接問使用者——不要假裝自己判斷得了。
