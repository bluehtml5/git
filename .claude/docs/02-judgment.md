# 判斷力外化：五個關鍵判斷的 rubric

> 這份檔案把「經驗豐富的模型憑感覺做的判斷」翻譯成可逐條核對的判準。每條附一個正例（該這樣）和一個反例（不該這樣）。遇到 rubric 沒涵蓋的情況：預設保守（問使用者 > 硬猜）。

## 1. 何時該升級模型

**判準**：任務需要的是「判斷」而不是「執行」時升級。具體訊號（任一成立即升級）：
- 你發現自己在兩個以上的合理做法之間猶豫，且選錯的代價 > 重做一次的成本。
- 錯誤訊息你讀完仍不明白根因，只能猜。
- 任務描述有多種讀法，且無法從 repo 或對話中排除歧義。
- 依 `01-delegation.md` 升降級路徑觸發（haiku 錯 1 次、sonnet 同任務錯 2 次）。

✅ **正例**：測試失敗，錯誤訊息指向一個你不理解的並發問題，改了兩次都沒中 → 帶著兩次失敗軌跡升級 opus。
❌ **反例**：要把 15 個檔案裡的舊 API 名稱換成新名稱，模式完全明確 → 這是執行不是判斷，用 sonnet/haiku 就好，升級是浪費。

## 2. 何時算「真的完成」

**判準**：以下全部成立才算完成，缺一即未完成：
1. 使用者原始要求的每一項都有對應產出（回頭重讀原始訊息逐項勾，不是憑印象）。
2. 產出經過**非自己**的驗證：verifier read-back、測試通過、或實跑成功（見 `01-delegation.md` 第 6 節）。
3. 工作已 commit + push（沒 push 的等於沒做）。
4. 給使用者的總結已寫好：改了什麼、為什麼、怎麼用。

✅ **正例**：「修好登入 bug」→ 改了程式碼、新增的測試通過、原有測試沒壞、push 完成、總結寫明根因 → 完成。
❌ **反例**：程式碼改完、自己重看一遍覺得沒問題、還沒跑測試就回報「已修復」→ 未完成。「看起來對」不是驗證。

## 3. 何時該停下來問使用者

**判準**：滿足任一就問（用 AskUserQuestion，附足夠 context 讓使用者不用回頭翻對話就能答）：
- 動作**難以回復**且不在原始要求的明確範圍內：刪東西、強制 push、對外發布、動到不是自己建立的檔案且內容與描述不符。
- 兩個解讀會導向**不同的產出**，且做錯要整個重來。
- 依 `01-delegation.md`：兩輪本質不同的做法都失敗。
- 發現原始要求本身可能是錯的（例如使用者要求修 A，但證據顯示問題在 B）→ 報告發現，不要擅自改成做 B。

**不該問的**（自己決定就好）：可回復的實作細節、有慣例可循的選擇（命名風格照既有程式碼）、問了也只會得到「你決定」的問題。

✅ **正例**：使用者說「清掉舊的設定檔」，但你發現那個檔案還被三處引用 → 停下來問，附上三處引用位置。
❌ **反例**：實作時猶豫函式該放 utils.py 還是新開檔案 → 這是可回復的細節，照 repo 既有慣例決定，不要問。

## 4. 什麼訊號代表方向錯了（該換路，而非重試）

**判準**（任一成立 = 這條路關閉，重試無意義）：
- 修好 A 冒出 B，修好 B 又冒出 C——連鎖新錯誤是「做法與現實不合」的訊號，不是「快好了」。
- 你開始需要愈來愈多特例（if/else、hack、註解解釋為什麼這樣寫）才能讓做法成立。
- 第二次失敗的錯誤訊息和第一次**相同** → 你根本沒動到根因。
- 做法依賴一個你沒驗證過的假設，而你已經找不到證據支持它。

**換路的動作**：先寫下「原路失敗的根本原因」一句話，再列出至少兩個本質不同的替代路線選一個。寫不出根本原因 → 你還不懂問題，先升級模型診斷，不要再動手。

✅ **正例**：改設定檔讓測試通過，連改三個參數都失敗且錯誤相同 → 停手，懷疑測試根本沒讀這個設定檔，先驗證「設定檔有被載入」這個假設。
❌ **反例**：同一個 flaky 測試重跑第 4 次期待它過 → 這不是換路也不是有效重試，是賭博。

## 5. 品質底線怎麼驗

**最低驗收線**（所有產出通用，由 verifier 執行）：
- 檔案真的存在、完整、非截斷；內文引用的路徑／工具名／命令全部真實存在。
- 程式碼：至少實跑過一次快樂路徑；有測試就必須跑，貼輸出。
- 文件：一個沒讀過對話的人能照著做。檢法：挑文中任一條指令自己跑一遍。
- 對外內容（PR、comment、報告）：沒有內部代號、沒有半成品段落、沒有「TODO」。

✅ **正例**：寫完部署文件後，verifier 照文件從第一步跑到第三步，卡在第二步的路徑錯誤 → FAIL，修正後再驗 → PASS。
❌ **反例**：verifier 只檢查「檔案存在且很長」就給 PASS → 長度不是品質，逐條對驗收條件才是。

## 品味題處理（誠實條款）

命名取捨、架構風格、文案語氣、「使用者其實想要什麼」——這類問題**上面的 rubric 補不了**，checklist 只能防災難，不能產生好品味。遇到時按序：
1. repo 裡有既有慣例 → 照抄慣例，不發明新風格。
2. 沒有慣例、決策影響大 → 產 2-3 個候選＋各自 trade-off，派 `opus`（可用時 `fable`）評審，或直接把候選拿給使用者選。
3. 以上都不可行 → 明說「這是品味判斷，我的選擇是 X，理由是 Y，不確定度高」，讓使用者有機會否決。禁止把猜測包裝成自信結論。
