# 模型調度守則

> 適用對象：主對話裡的模型（不論等級）。核心思想：**主對話是指揮所，不是工地。** 主對話的 context 是全 session 最貴的資源，只放決策、結論、與使用者的對話。

## 1. 指揮官不下場

以下工作**一律派 subagent**，主對話只收結論：

- 掃 repo / 找「某功能在哪實作」/ 需要開 3 個以上檔案才能回答的問題 → `Explore`
- 查網頁、讀文件、做研究 → `general-purpose`
- 批次改檔（同一模式套用到多處）→ `general-purpose`
- 驗收產出 → `verifier`（見 `.claude/agents/verifier.md`）

主對話**可以自己做**的：改 1-2 個已知位置的檔案、跑單一命令、git 操作、回答不需查資料的問題、以及最多 2 次「定向查找」（你已經知道檔名或精確關鍵字的 Grep/Read）。第 3 次查找 = 你其實在探索，派出去。

## 2. 派工三件套（每次派工的 prompt 必含）

1. **目標與動機**：要做什麼＋為什麼要做（subagent 看不到主對話，沒有動機它會在邊界情況亂猜）。
2. **驗收條件**：可機械檢查的完成判準。壞範例：「找出相關程式碼」。好範例：「回報每個呼叫 `parseConfig` 的位置，格式為 `檔案:行號 + 一行說明`；若超過 20 處，只列前 20 並回報總數」。
3. **回報格式**：明確規定回什麼、不回什麼（見第 4 節回報合約）。

模板直接抄 `03-prompt-templates.md`，不要即興發揮。

## 3. 模型與 effort 的顯式指定

**可用機制**（2026-07 查證於官方文件與本環境 Agent tool schema）：
- Agent tool 呼叫時的 `model` 參數：`haiku` / `sonnet` / `opus` / `fable`。`fable` 在枚舉中但屬於受限模型，不保證這個帳號能跑：試一次，失敗就退 `opus`，並在 lessons.md 記下結果。
- 自訂 agent（`.claude/agents/*.md`）frontmatter：`model:`（同上值，另接受完整 model ID 與 `inherit`）＋ `effort:`（`low`/`medium`/`high`/`xhigh`/`max`，可用級別依模型而定）。
- 解析順序：`CLAUDE_CODE_SUBAGENT_MODEL` 環境變數 > 呼叫時參數 > frontmatter > 繼承主對話。

**派工選型表**：

| 任務型態 | model | 理由 |
|---|---|---|
| 機械性查找（grep 已知關鍵字、列檔案、read-back 驗證） | `haiku` | 不需判斷，只需執行 |
| 一般探索、實作、批次套用已定型的模式、**驗收**（= 照驗收條件逐條機械核對，用 `verifier`，定義檔已設 sonnet/high） | `sonnet` | 性價比主力 |
| 除錯卡關、架構決策、**審查**（= 開放式評估好壞、找設計問題，沒有逐條清單可核對）、模糊需求釐清 | `opus` | 需要判斷力 |
| 品味題、多方案評審、opus 也卡住的問題 | `fable`（可用時）否則 `opus` + 多答案評審（見 `02-judgment.md`） | 最後手段 |

**effort**：只有自訂 agent 能設。`verifier` 固定 `high`（驗收寧可慢）。臨時派工用內建 agent 時無法指定 effort，靠選對 model 補。

## 4. 回報合約（寫進每個派工 prompt）

- 只回：結論、`檔案:行號` 引用、明確的失敗說明。
- 不回：檔案全文、工具原始輸出、過程流水帳。
- 長產物（報告、大段程式碼、清單超過 30 行）：寫到檔案裡，回傳路徑＋3 行摘要。
- 失敗時：回報「試了什麼、每次的確切錯誤訊息、卡在哪」，不要只回「做不到」。

## 5. 升降級路徑

- **haiku 錯 1 次** → 直接升 `sonnet` 重派，不重試。haiku 便宜，錯了再教的成本高於直接升級。
- **sonnet 同一子任務連錯 2 次** → 升 `opus`，且派工 prompt 必須附**完整失敗軌跡**：兩次分別怎麼做的、確切錯誤輸出、目前的假設。沒有軌跡的升級 = 讓 opus 重走一遍死路。
- **opus 也解不了** → 停下來報告使用者，附失敗軌跡。不要無限升級硬撐。
- **降級**：高階模型解出一個「可複製的模式」（例如：修法確定、只是要套到 15 個檔案）→ 把模式寫成明確步驟，降回 `sonnet`/`haiku` 批次套用，再派 `verifier` 抽驗。
- **全域上限**（與 CLAUDE.md 硬規則 2 同一套算法）：單一做法最多試 2 次；同一件事不論換了幾個模型，最多 2 條「本質不同的做法」路線，即全案累計最多 4 次嘗試。之後必須報告使用者。

## 6. 驗證不自驗

做的人不能當驗收的人——同一個 context 會用同一套盲點看自己的產出。（唯一豁免同 CLAUDE.md 硬規則 3：純錯字／格式／單行文件修正可自己 read-back，不必派 verifier——這也化解了與「小事別派工」反模式的表面衝突：有實質內容的產出一律外驗，瑣事自查。）

- **檔案類產出**：派 `verifier`（fresh context）read-back：檔案存在？內容完整（非截斷）？和驗收條件逐條對得上？
- **程式碼**：測試或實跑是第一驗證（能跑就不要用「看起來對」）。verifier 負責確認測試真的跑過且涵蓋改動點，而不是重看程式碼。
- **高風險判斷**（判定用 `02-judgment.md` 的「高風險清單」，任一命中即是）：加第二意見——派一個沒看過第一版結論的 agent 獨立解同一題，比對答案；或產 2-3 個候選答案，派 `opus` 當評審選優並說明理由。
- verifier 回報「不通過」時：修完必須**再驗一次**，不能修完就宣告完成。

## 7. 反模式（看到自己在做這些就停）

- 派工 prompt 只有一句話（缺三件套）。
- subagent 回了 200 行原始資料，你照單全收貼進對話。→ 下次派工時把回報合約寫清楚。
- 為了一個 5 分鐘的小改動派 subagent。→ 派工本身有固定成本（冷啟動、重建 context），小事直接做。
- 同時派 5 個 agent 但任務彼此相依。→ 只有互相獨立的任務才平行派。
